## Meeting Notes

The team reviewed the HTML to QML UI conversions, agreed on window sizing and
file structure conventions, and scoped the sprint for iteration two. Build
environment decisions were settled and a unit conversion gap was identified.

### UI Conversion and Styling

Both Landis and Kevin converted their HTML mockups to QML by handing the markup
to AI along with the styling guide. The conversions were straightforward and took
well under a day. Landis's pages are all updated and readable, and Kevin
demonstrated his working version, which mirrors the HTML structure using layout
objects (columns, cards, buttons) much like any UI design language. Styling is
applied through reusable component definitions (e.g., `AppButton`) with the theme
defined separately in `theme.py`.

The target for Wednesday is a UI coded in Python, cleaned up per module, rather
than just the styling guide applied to static mockups.

Windows must enforce a minimum size of **720 × 450 px** at a **16:10 aspect
ratio** so the layout cannot be shrunk to the point of being unusable. Kevin's
resizing was misbehaving at the start of the call but was working by the end.

### File Structure

There is currently no consistent structure — Kevin put everything under a
`train model` folder since his conversion started as an experiment to see whether
the tooling was good enough. The current working file structure
was sent in Discord and should be consistent across all modules. 

Each model should live in its own folder so the repository collapses down to a
small number of top-level items. The team agreed to establish this convention
early so everyone follows the same pattern. Everyone should also be developing
on separate branches from this point forward.

### Button Interaction

The UI buttons currently do nothing — there is no backend at all, only visual
state changes. For the Wednesday demo, each button should call a function that
prints to the terminal so it is visible that the interaction is wired up. Kevin
will look into PySide's button press events and report back to the team.

**Update:** Kevin sent Braden a breakdown of how button press 
events are handled in QML. This will also be sent to the rest of the team.

### Sprint Scope

The sprint runs through iteration two. Deliverables per module:

- UI coded in Python with minimum window sizing enforced
- Key inputs and outputs functional
- Other inputs and outputs functional
- A separate test UI that drives those inputs and outputs

The test UI does need to work, since iteration two is where each subsystem is
demonstrated individually with the test UI driving its outputs.

Defining protocols for the module interfaces was added to the sprint so there is
an agreed interface based on the architecture inputs and outputs.

Module-specific tasks will be added to the board as implementation progresses,
since the team does not yet know enough about the details to break them down now.

### Build Environment

The team decided **against Docker** for this project. The final executable has to
run on Windows and the chosen compiler is not a cross-compiler, so the build has
to happen on a Windows machine — which defeats the purpose of a Linux/WSL-based
container. A virtual environment with a requirements file is sufficient, and it
avoids friction for members who have never used Docker.

The bash/PowerShell script item stays in the sprint. Scripts are still useful for
coordinating tasks like running PyLint and building, and the team intends to use
GitHub Actions with a Windows runner rather than a Linux one. Landis described the
NPM-style approach of aliasing long build commands into short named scripts
(`npm run dev`, `npm run build:all`); the team agreed this is the same idea as
the shell scripts already planned, so no separate item was added.

Landis proposed a `/setup` startup command for new AI sessions that loads project
specifications into memory and verifies dependencies are up to date before
development begins. Kevin is already working on this as part of the
`instructions.md` single-source-of-truth effort: the startup command will point to
an index file that pulls in only the relevant documents, avoiding context bloat
from loading everything.

**PyInstaller** was discussed as the packaging tool. Braden wanted to iron it out
early to avoid friction later, but the team agreed it is not needed this
iteration since they can present from their own machines. It will be dropped into
the backlog for later sprints rather than added to this sprint, with
the caveat that it should not be left until the day before the executable is due.
It is also not fully settled whether running as a Python script will behave
identically to the packaged executable.

### Units

Landis's UI showed a suggested speed limit in meters per second, but all user
interfaces are supposed to display imperial units (miles per hour) with metric on
the backend. The root cause is `common/units.md`, which currently instructs every
agent to use meters per second across the board; Kevin hit the same issue on his
own UI. There are also some kilometers per hour scattered in there.

The fix is to split the file into separate backend and frontend unit tables plus
a conversion table, since each conversion is just a constant multiplier.

### General
