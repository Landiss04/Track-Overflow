## Meeting Notes

The team aligned on UI architecture, interaction diagrams, and input/output
definitions for each module in preparation for tomorrow's presentation.

### UI Architecture

The team agreed on a central homepage that runs continuously (like the train
simulation) and acts as a directory to launch each module independently. Modules
update separately rather than re-rendering the full system, which mirrors the
approach other groups have taken.

Each module also needs a configurable test UI for debugging, with override
controls to force inputs and observe outputs. This test screen should use its own
dedicated clock so module behavior can be isolated from the global simulation
clock.

### Interaction Diagrams

It is unclear whether the "information architecture" requirement means an
interaction diagram, so the team will include one per module to be safe, along
with reasoning for UI element grouping and ordering.

Hardware and software interaction diagrams may be merged if they are functionally
identical; otherwise each UI gets its own. Teams will compare their diagrams and
decide.

### Key Inputs and Outputs

Key inputs are elements the user interacts with that are vital to system
operation (e.g., PLC program selection, mode switches). Other inputs/outputs
cover data passed between modules or non-essential UI elements. The distinction
depends on core functionality combined with user interaction, not strictly on
literal user-entered controls.

Key input/output tables belong on the slides only, not in Figma.

### Presentation

Slide headers, text boxes, and image formatting currently vary across sections
and need to be unified (e.g., splitting long titles into two lines). Each module
will be presented in sequence: persona introduced once, then interaction diagram,
key inputs/outputs, and design rationale per module.

A final review meeting is scheduled for ~5:30 PM tomorrow before class to polish
the deck and confirm styling.
