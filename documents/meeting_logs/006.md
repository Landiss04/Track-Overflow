### Architecture Diagram

Braden and Landis confirmed their inputs and outputs match. Additional data from
Braden's module will be folded into the status report rather than broken out
individually, which also addresses Alec's feedback about consolidating inputs
shown in the presentation.

**Switch states.** Deni needs the current position of infrastructure elements
(switches, lights), not just the commanded state. Rather than each module storing
its own copy, the wayside will query the track model (e.g., `get_track_switch`)
for current state. The existing diagram stays as is.

**Passengers at station.** A block showing passenger activity sent from the train
model to the track model was determined not to belong there — the track model
handles passengers boarding and deboarding internally.

**Block occupancy.** The main open question was how the track model knows where
a train is, since in the real world that comes from the track circuit. The
resolution: each block carries an orientation boolean (polarity), which the track
model sends to the train model through the track circuit. When the train sees
that boolean flip, it knows it has crossed into a new block and fires a **block
change event** to the track model. The track model then maintains train position
and block occupancy from those events. Deni noted switches may complicate
alternating polarity since there are three options, but that will be handled
during implementation.

**Actual speed.** Kevin questioned whether the track model still needs actual
speed now that block changes are event-driven, since a physical track would not
know a train's speed. Alec had previously said to include it, and Ivan suggested
it could serve as redundancy for estimating speed from block transitions, so it
stays on the diagram for now.

**Ticket sales.** Landis confirmed the new ticket sales communication line is
one-way — the track model is not sending anything back.

Kevin has already made the diagram changes, and Jonathan updated the team Figma
to match.
