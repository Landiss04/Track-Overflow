The Input and Output Cards are the physical I/O boundary of the chassis — every signal crossing into or out of the module passes through one of them.
Raw I/O is decoded and encoded by the OS layer before the program ever sees it; the program itself only reads and writes typed values.
Track Controller and Train Model are bidirectional peers. The controller sends commands (speed, authority, switches, crossings, lights) and receives block occupancy, switch, crossing and signal states, and track failure status.
Train Model reports actual train speed, and receives the Track Signal struct. The track layout is loaded once from the JSON configuration.
Track Controller is the source of Track Heater Command (it owns the same wayside PLC logic that drives switches and crossings) and, in return, reads back Track Heater State — the same bidirectional pattern as its other commands and states.
Environmental Temperature is not an external command: Track Model computes the live per-block temperature itself, seeded by an Ambient Weather Feed read once as a baseline. Everything downstream (heater engagement, speed restrictions) reacts to Track Model's own number, not a raw pass-through.
Random Ticket Sale works the same way — each station rolls this per-tick chance and Track Model decides whether a new waiting passenger appears, so ticket sales are generated inside the module rather than commanded from outside. When a train is present, Track Model moves waiting passengers onto it and reports that count to Train Model as Passengers Boarding, so Train Model's own onboard count stays in sync; Ticket Sales (the revenue side of the same event) goes to CTC Office.
Signal State is sent directly to the Train Controller (onboard), separate from the Track Signal struct sent to Train Model — the Train Controller only needs the current aspect ahead for cab-signaling and speed regulation, not the full commanded-speed/authority/beacon/block-info payload.
