## 2. Editability rules

The person who receives this file will keep editing it in draw.io. Build it from
draw.io's own shapes, so every box, label and line can be selected, moved, retyped and
restyled there.

- **No images.** Don't embed images, SVGs or PNGs of diagrams, and don't draw text as
  paths. Every word must be a live label.
- **Shapes from the UML palette.** Use draw.io's built-in UML shapes (styles in
  section 3). Don't fake a shape by grouping primitive lines.
- **Connected edges.** Every edge has `source` and `target` set to the cells it joins,
  so it follows them when they move. Use waypoints only where a straight line would
  cross another shape. Sequence messages are the one exception; see 3.3.
- **Containers own their contents.** Packages, the use-case subject, deployment nodes
  and lifelines are containers (`container=1`). Their contents are child cells
  (`parent=` the container's id), so moving a container moves everything in it.
- **Editable class members.** Use draw.io's stacked "Class" shape: a header, then one
  text cell per compartment, with members on separate lines (`html=1`, `<br>`
  between lines).
- **Stereotypes are text.** Write them with guillemets, e.g. «dataclass, frozen».
- **Fonts.** Use the default font (Helvetica 12) throughout. Every label must fit
  inside its shape at that size; grow the shape rather than letting text spill out.
- **IDs.** Give every cell a readable `id`, such as `uc-validate`, `cls-TrainConfig`
  or `msg-14`. That makes the XML editable by hand and your own checks easier.

## 4. What the module is

You need this background to label things correctly. It isn't something to draw.

- **What it is.** The Train Model is the physics simulation of one train in a
  five-module course project. The other four modules are the CTC Office, Track
  Controller, Train Controller and Track Model. These diagrams cover the Train Model
  module only, not the whole system. Two other modules appear only as outside actors:
  the Train Controller sends it commands, and the Track Model sends it track data.
  The CTC Office and Track Controller don't appear at all.
- **How it's driven.** It is stepped from outside: `step(dt, inputs) -> outputs`, with
  a fixed dt. A shared simulation clock ticks every 0.1 s at 1× or 10×; speed changes
  how often ticks come, never dt.
- **What it doesn't do.** It is physics only. It doesn't regulate speed, enforce the
  70 km/h maximum, cut traction under braking, or enforce a door interlock. All of
  that is the Train Controller's job.
- **Integrated process.** The Train Model module process holds its fleet, physics
  and window; the harness supplies the sole clock and all mapped inputs. The
  separate removable developer utility is documented at the end, outside diagrams.
- **Failures.** A user called "Murphy" injects three failures from the Train Model
  window: engine, signal pickup and brake.
  - Engine failure zeroes traction.
  - Brake failure blocks the service brake only.
  - Signal-pickup failure zeroes the commanded speed and authority passed through to
    the Train Controller.
  - Failures are **not** reported to the Train Controller.
- **Passenger emergency brake.** A passenger can pull it from the window. It latches.
  It clears when the Train Controller's `emergency_brake` goes from true to
  false. The window has no release.
- **Units and terms.** Backend values are SI, with grade in degrees and temperature in
  °C. Field names carry their units (`power_cmd_w`, `grade_deg`). The track signal
  carries **commanded speed**, never "suggested speed".

## 7. Page 3: Sequence, integrated tick

Title: **Train Model: one integrated harness tick**.

Lifelines: harness/SystemClock (external process), ModuleLink, TrainModelProcess,
TrainModelFleet, selected TrainModelState, physics TrainModel, and Main.qml.
Keep the clock outside the Train Model process; one fleet owns all per-train states.

1. Harness sends STEP with tick number, fixed dt, unwrapped end-of-tick `sim_time_s`,
   and roster-keyed inputs from direct producer-to-consumer edge mappings.
2. ModuleLink invokes `TrainModelProcess.step(tick, dt, sim_time_s, inputs)` on the
   owning Qt thread. Reject a malformed top-level trains object without stepping.
3. The adapter follows roster additions/removals and fans supplied time to the fleet
   for display, including the idle empty-fleet view. Identity/line are roster metadata.
4. For each train, establish its epoch once as first supplied timestamp minus dt,
   decode module-owned inputs, and validate before physics mutation.
5. `alt [valid train]`: state calls model.step. Validate; clear passenger latch if
   release is commanded; follow doors; draw disembark/board when eligible; detect
   polarity change; integrate exact constant-force and midpoint power-limited
   segments totaling dt; update temperature and accepted elapsed time; build outputs.
   `else [invalid train]`: preserve physics/output/random state and record rejection;
   other trains still advance. Display may still show current harness time.
6. State refreshes selected-train bindings. QML reads independent brake states,
   front offset, next station/platform, and fleet identity/line; no arrival field
   appears in the intended window.
7. `opt [tick % 15 == 0]`: compare epoch plus accepted elapsed model time against
   supplied unwrapped time for every train, including rejected trains. Use absolute
